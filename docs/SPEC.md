# 월드 다이스 투어 (World Dice Tour) — 게임 명세

로컬 네트워크(LAN)에서 즐기는 세계일주 주사위 보드게임. 호스트 PC가 서버를 띄우고 **방을 만들면, 같은 와이파이의 다른 기기(폰/태블릿/PC)가 브라우저로 접속**해 함께 플레이한다. 한 기기에 여러 명이 앉는 핫시트도 같은 방식으로 지원(한 기기가 좌석 여러 개 보유).
아이템/캐릭터/스킬 없음 — 주사위와 카드 운, 그리고 "살까/지을까/걸까" 선택만 있다.

## 0. 저작권 원칙

- 특정 상용 보드게임의 **명칭·카드 문구·보드 아트·칸 고유 명칭을 사용하지 않는다.** 모든 텍스트/디자인은 본 프로젝트의 창작물.
- 실제 도시명은 사실 정보이므로 사용 가능. 도시 구성/순서/가격은 독자적으로 설계한다.
- 카드 칸 이름은 **"행운 티켓"**, 감금 칸은 **"조난 섬"**, 자유이동 칸은 **"세계일주 공항"**.

## 1. 기술 스택

- 빌드 없는 Vanilla JS (ES Modules) + HTML + CSS. **런타임 의존성 0개** (npm 패키지 설치 불필요).
- 서버: Node 24 내장 `node:http`. 실시간 동기화는 **SSE(Server-Sent Events) + fetch POST** (WebSocket 라이브러리 불필요).
- 서버는 `0.0.0.0:5173`에 바인딩하고 시작 시 LAN 접속 주소(`http://192.168.x.x:5173`)를 콘솔에 출력. `PORT` 환경변수 지원.
- 테스트: Node 내장 러너 `node --test`.
- 저장: 서버가 방 상태를 `data/rooms/*.json`에 자동 저장(서버 재시작 후 이어하기). 클라이언트는 좌석 토큰만 `localStorage`에 보관(재접속용).

## 2. 아키텍처 (레이어 분리, 서버 권위)

**게임 상태와 모든 난수(주사위/티켓/카지노)는 서버에만 존재**한다. 클라이언트는 커맨드를 보내고 DTO 스냅샷+이벤트를 받아 그리기만 한다.

- 도메인은 `RandomSource`(`nextInt(min,max)`), `RoomRepository`(`save/findByCode/findAll/delete`) 인터페이스에만 의존. 테스트는 결정적 가짜 구현 주입.
- 비즈니스 로직은 엔티티/도메인 서비스 안에 캡슐화(빈약한 도메인 모델 금지). 애플리케이션 Service는 조합만.
- **모든 돈 이동은 `MoneyIntent` 한 종류로 표현되고 `Treasury` 한 곳에서만 적용된다.** 11장 참고.
- 에러 응답은 `{ code: "ERR0xx", message }` 규격만 반환. 스택/내부 메시지는 서버 로그로만. 빈 catch 금지.
- 클라이언트는 서버에서 온 문자열(이름 등)을 `textContent`로만 출력(innerHTML에 외부 문자열 금지).

### 2.1 방/좌석/권한 모델 (LAN)

- **방(Room)**: 4자리 코드(`[A-HJ-NP-Z2-9]{4}`, 헷갈리는 문자 제외). 상태 `LOBBY → PLAYING → FINISHED`. 방 목록 조회로 LAN 게임 목록처럼 참가.
- **좌석(Seat)**: 방 안의 플레이어 자리(2~4). 종류 `HUMAN | COMPUTER`. 좌석을 만들면 서버가 **좌석 토큰**(crypto 랜덤 32바이트 hex)을 발급 — 이 토큰을 가진 기기만 그 좌석의 커맨드를 보낼 수 있다. 한 기기가 좌석 여러 개를 가질 수 있음(핫시트).
- **호스트**: 방을 만든 좌석. 호스트 토큰만 게임 옵션 변경/컴퓨터 좌석 추가/시작/좌석 강퇴(대기실에서만)/**오프라인 좌석을 컴퓨터 자동 진행으로 전환** 가능.
  - 자동 진행 **켜기**는 그 좌석이 오프라인일 때만(이중 조종 방지). **끄기**는 호스트 또는 그 좌석 본인이 할 수 있다.
  - 자동 진행 중인 좌석의 게임 커맨드는 사람이 직접 보낼 수 없다(먼저 끄고 조종권을 회수한다).
  - 좌석 삭제는 **대기실에서만** 가능하다. 게임 중 "나가기"는 접속만 끊는 것이며, 남은 사람들은 호스트가 그 좌석을 자동 진행으로 돌려 계속한다.
- **권한 검증은 Service/도메인에서**: 모든 게임 커맨드는 `토큰 → 좌석 → 현재 턴 플레이어 일치 + 현재 페이즈 허용 커맨드` 검증. 토큰 비교는 `crypto.timingSafeEqual`. 토큰은 어떤 DTO/SSE/로그에도 싣지 않는다.
- 접속 끊김: SSE 연결 수로 좌석 온라인 여부 표시. 재접속 시 localStorage 토큰으로 좌석 복구.

### 2.2 API

| 메서드/경로 | 설명 |
|---|---|
| `GET /api/server-info` | LAN 접속 URL 목록(로비에 "다른 기기에서 이 주소로 접속" 안내용) |
| `GET /api/rooms` | 참가 가능한 방 목록(RoomSummaryDto) |
| `POST /api/rooms` | 방 생성 `{ hostName }` → `{ room, seatId, seatToken }` |
| `POST /api/rooms/:code/seats` | 좌석 참가 `{ name }` → `{ seatId, seatToken }` (LOBBY에서만) |
| `DELETE /api/rooms/:code/seats/:seatId` | 본인 퇴장 또는 호스트 강퇴 |
| `POST /api/rooms/:code/host-actions` | `{ type: ADD_COMPUTER \| SET_OPTIONS \| START \| SET_AUTOPILOT, ... }` |
| `POST /api/rooms/:code/commands` | 게임 커맨드 `{ seatId, type: ROLL \| BUY \| SKIP_BUY \| BUILD \| SKIP_BUILD \| CASINO_BET \| CASINO_LEAVE \| ISLAND_PAY \| ISLAND_ROLL \| TRAVEL \| SELL \| ... , payload }` |
| `GET /api/rooms/:code/events` | SSE 스트림: `room`(로비 변경), `game`(GameViewDto + 이번 커맨드의 이벤트 목록) |

- 인증 헤더 `Authorization: Bearer <seatToken>`. 입력 검증(화이트리스트): 이름 `^[가-힣a-zA-Z0-9 ]{1,10}$`, 방 코드 정규식, 커맨드 type enum, 베팅액 정수·단위·범위, 목적지 0~39 정수 등. 알 수 없는 필드는 무시.
- 컴퓨터 좌석/자동 진행 좌석의 턴은 서버가 짧은 지연(연출용 ~800ms)을 두고 AutoPlayerPolicy로 진행.

## 3. 기본 규칙

- 화폐 단위 원. 시작 자금 **10,000,000원**(D46, 원래 3,000,000). 출발 칸을 **지나거나 도착**하면 월급 **200,000원**.
- **바퀴(lap)**: 모든 플레이어는 1바퀴에서 시작하고, **월급을 받는 상황마다**(= 앞으로 이동하며 출발 칸을 지나거나 도착) 1바퀴씩 올라간다. 월급이 대출 상환에 압류돼도 바퀴는 오른다. 뒤로 밀려 출발 칸에 도착하거나 조난 섬으로 이송되면 오르지 않는다(D1과 같은 기준). 바퀴 수가 **지을 수 있는 건물**을 정한다(4장).
- 주사위 2개. **더블이면 한 번 더**. 3연속 더블이면 즉시 조난 섬으로.
- 승리: 마지막까지 파산하지 않은 1인. 설정에서 **라운드 제한(없음/20/30)** 선택 가능 — 제한 도달 시 총자산(현금+도시 매입가+건설비) 1위 승리.
- 좌석은 사람 또는 **컴퓨터(단순 규칙 기반)**: 컴퓨터 의사결정은 application 레이어의 `AutoPlayerPolicy`로 분리한다.
  - 매입: 현금이 가격의 2배 이상이면 구매.
  - 건설: 건설 후에도 현금이 300,000원 이상 남는 범위에서 **가장 비싼 조합**을 짓는다(서버가 준 선택지 중 **잠기지 않은 것만** 고른다). 관광명소는 현금이 건설비의 2배 이상일 때 짓는다.
  - 인수: 현금이 인수 가격의 3배 이상이면 인수.
  - 출발 칸 보너스: 내 도시 중 **가격이 가장 높고 지을 수 있는 것이 있는** 도시를 고른다.
  - 카지노는 최소액으로 1회, 공항은 빈 도시 중 최고가로 이동.
  - 지불 불능: `AUTO_SELL` → 그래도 부족하면 `TAKE_LOAN`(가능할 때) → 그래도 부족하면 `DECLARE_BANKRUPTCY`.

### 도시(CITY)
- 빈 도시에 도착 → 구매 여부 선택(가격 지불).
- 도시에는 **독립적인 건물 3종**(별장 VILLA / 빌딩 BUILDING / 호텔 HOTEL)과 **관광명소(LANDMARK)** 가 있다.
  - 건설비: 별장 = 가격 × 0.3, 빌딩 = 가격 × 0.6, 호텔 = 가격 × 0.9, 관광명소 = 가격 × 1.0 (원 단위 내림).
- **바퀴별 건설 제한**: 건설하는 사람의 **현재 바퀴 수**가 지을 수 있는 건물을 정한다(누적).

  | 바퀴 | 지을 수 있는 건물 |
  |---|---|
  | 1바퀴 | 별장 |
  | 2바퀴 | 별장 · 빌딩 |
  | 3바퀴 이상 | 별장 · 빌딩 · 호텔 |

  - 종류 사이의 **순서는 필요 없다**(3바퀴 플레이어는 별장 없이 호텔만 지어도 되고, 3종을 한 번에 지어도 된다). 건물 3종은 여전히 서로 독립이다.
  - **관광명소는 바퀴로 막지 않는다** — "그 기회가 시작될 때 이미 3종이 모두 있는가"만 본다(따라서 스스로 3종을 지었다면 자연히 3바퀴 이상이다. 예외는 **인수**로 넘겨받은 건물이 섞여 3종이 채워진 경우인데, 이때는 인수자의 바퀴와 무관하게 관광명소가 제안된다 — D23).
  - 인수한 도시의 **건물은 인수자의 바퀴와 무관하게 그대로 남는다.**
- **건설 기회(build opportunity)**: 아직 짓지 않았고 **그 바퀴에 열린** 별장/빌딩/호텔 중 **원하는 조합을 한 번에** 지을 수 있다(합계 지불).
  - 건설 기회가 시작될 때 이미 3종이 모두 있으면, 그 기회는 **관광명소 업그레이드**만 제안한다(3종을 완성한 그 기회에서 관광명소를 바로 짓지는 못한다).
  - 관광명소까지 지으면 더 건설할 수 없다.
  - 건설 기회가 주어지는 시점: (a) 빈 도시를 매입한 직후(같은 턴), (b) 내 도시에 도착했을 때, (c) 도시를 인수한 직후, (d) 출발 칸 보너스.
  - **그 바퀴에 지을 수 있는 것이 하나도 없으면 기회를 열지 않고 넘어간다**(예: 1바퀴인데 별장이 이미 있는 도시). 현금이 모자랄 때와 같은 처리다.
  - 잠긴 건물을 커맨드로 요청하면 규격 에러로 거부하고 상태는 바뀌지 않는다(서버가 유일한 권위).
- 남의 도시 도착 → 통행료 지불. 통행료 = 가격 × 배율(원 단위 내림): 땅만 `0.1`, 별장 `+0.3`, 빌딩 `+0.6`, 호텔 `+1.0`(3종 모두 = `2.0`), 관광명소는 `3.5` 고정.

### 출발 칸 보너스
- 출발 칸을 **지나가는** 것이 아니라 **정확히 도착**하면(주사위·티켓·공항 이동 모두 해당) 월급과 별개로, 자기 도시 중 하나(관광명소 완성 도시 제외)를 골라 **건설 기회 1회**를 받는다.
- 후보 목록에는 **그 바퀴에 지을 것이 하나라도 있는** 도시만 올라간다. 건설 가능한 도시가 없으면 자동으로 넘어간다.

### 인수(ACQUISITION)
- **관광명소가 없는 남의 도시**에 도착해 통행료를 전액 지불한 뒤, 방문자는 그 도시를 **인수**할 수 있다(소유자는 거절할 수 없다).
- 인수 가격 = (매입가 + 투자한 건설비 합계) × 2. 현재 소유자에게 지불한다.
- **보유 현금으로만** 인수할 수 있다(인수 자금 마련을 위한 매각/대출 불가).
- 건물은 도시와 함께 넘어간다. 인수 직후 새 소유자는 건설 기회를 얻는다.
- 관광명소 도시와 휴양지는 인수할 수 없다.
- 도시의 `invested`(매입가 + 정가 기준 건설비 합계)는 인수 후에도 **정가 기준**으로 유지되며, 매각 환급액은 계속 `invested × 0.5`다.

### 휴양지(RESORT)
- 구매만 가능, 건설 불가. 통행료 = 50,000 × (소유자가 가진 휴양지 수). 

### 세관(TAX)
- 현금의 10%(내림, 최소 0)를 납부. 납부액은 **카지노 잭팟 적립금**에 쌓인다.

### 조난 섬(ISLAND)
- 도착(또는 3연속 더블/티켓으로 이송)하면 조난. 최대 3턴 동안 자기 턴에 선택: **구조비 200,000원 지불 후 정상 굴림** 또는 **주사위 굴리기(더블이면 탈출해 그 눈만큼 이동, 추가 턴 없음)**. 3번째 실패 턴이 끝나면 다음 턴에는 자동 탈출.
- 조난 중에도 통행료는 받는다.

### 세계일주 공항(AIRPORT)
- 도착하면 **다음 자기 턴에** 주사위 대신 원하는 칸(공항 칸과 현재 칸 제외)을 골라 이동. 출발을 지나면 월급 지급. 도착 칸 효과 정상 적용.
- 공항 칸에 도착하면 **더블이어도 추가 턴 없이** 그 턴이 끝난다(조난과 같은 취급).

### 라스베이거스 카지노(CASINO)
- 도착 시 한 방문에 **최대 3판**, 언제든 그만두기 가능. 베팅액: 10,000원 단위, 최소 10,000 ~ 최대 min(보유현금, 500,000).
- 게임 3종 (모두 RandomSource로 판정):
  1. **홀짝**: 주사위 1개. 맞히면 ×2 (베팅액 포함 환급).
  2. **하이로우세븐**: 주사위 2개 합. 로우(2~6) ×2, 하이(8~12) ×2, 세븐(7) ×5.
  3. **슬롯**: 3릴, 심볼 6종(🍒🍋🔔⭐💎7️⃣) 균등. 3개 일치 ×10, 2개 일치 ×1.5(내림), 7️⃣7️⃣7️⃣이면 ×10 + **잭팟 적립금 전액**.
- 잃은 베팅액의 절반(내림)은 잭팟 적립금에 쌓인다. 잭팟 초기값 0.
- 적립금이 나가는 길은 둘이다: 슬롯 7️⃣7️⃣7️⃣(1/216)과 **행운 티켓의 잭팟 수령권 2장**(5장 참고·D25). 카지노에 다시 오지 않아도 쌓인 돈이 판으로 돌아온다.

## 5. 행운 티켓 (22장, 즉시 효과만 — 보관형 카드 없음)

문구는 전부 자체 창작. 예시(구현 시 22장을 채울 것):
- 복권 소액 당첨 +100,000 / 여행 브이로그 대박 +200,000 / 면세점 환급 +50,000 / 여행자 보험금 +150,000
- 수하물 초과 요금 −50,000 / 여권 재발급 −100,000 / 호텔 미니바 폭주 −80,000 / 과속 딱지 −60,000
- 순풍: 앞으로 3칸 / 역풍: 뒤로 2칸 / 출발 칸으로 직행(월급 수령) / 카지노 초대장: 라스베이거스로 이동(출발 지나면 월급)
- 폭풍우: 조난 섬으로 이송(월급 없음) / 공항 특가: 세계일주 공항으로 이동
- 생일 축하: 다른 모든 플레이어에게서 50,000씩 받음 / 한턱 쏘기: 다른 모든 플레이어에게 30,000씩 줌
- 건물 점검: 내 건물 단계 합계 × 40,000 지불 / 관광 붐: 내 도시 수 × 30,000 수령
- 가장 가까운 휴양지로 전진 / 세무조사: 현금의 5% 납부(잭팟 적립)
- **잭팟 당첨권: 잭팟 적립금 전액 수령 / 잭팟 나눔 행사: 잭팟 적립금의 절반(내림) 수령** — 적립금이 0원이면 아무 일도 일어나지 않는다(위로금 없음)

이동형 티켓은 도착 칸 효과를 정상 적용한다(연쇄는 같은 규칙으로 처리, 무한 루프 방지).

## 6. 지불 불능(INSOLVENCY)과 파산

현금이 부족한 것 자체가 즉시 파산은 **아니다**. 지불액 > 현금이면 **정리(AWAIT_LIQUIDATION) 페이즈**로 들어가고, 채무가 메워질 때까지 아래 커맨드를 반복해서 쓸 수 있다.

| 커맨드 | 설명 |
|---|---|
| `SELL` (선택매각) | 고른 자산 하나를 은행에 매각. 환급 = `invested × 0.5`(건물 포함 통째로, 주인 없는 초기 상태로 되돌아간다) |
| `AUTO_SELL` (자동매각) | 환급액이 가장 낮은 자산부터 서버가 자동 매각. 현금 ≥ 지불액이 되면(또는 남은 자산이 없으면) 멈춘다 |
| `TAKE_LOAN` (대출) | **게임당 플레이어별 1회.** 은행이 현금 1,000,000원을 빌려주고 채무 1,200,000원이 생긴다. 이후 받을 **월급은 전액 채무 상환에 압류**된다(상환 완료까지). 남은 채무는 라운드 제한 순위의 총자산에서 차감된다 |
| `DECLARE_BANKRUPTCY` (파산) | 이 페이즈에서는 **항상** 선택 가능. 남은 현금을 채권자(플레이어 또는 은행/잭팟)에게 주고, 모든 자산을 주인 없는 상태로 초기화, 해당 플레이어는 탈락 |

- 현금 ≥ 지불액이 되는 즉시 지불이 자동 완료되고, 중단된 턴 흐름이 이어진다(예: 통행료 지불 후의 인수 제안).
- 팔 자산이 없고 대출도 이미 썼다면 유효한 커맨드는 `DECLARE_BANKRUPTCY`뿐이다. 현재 선택 가능한 수단은 뷰 DTO가 알려준다: `liquidation: { amountDue, creditor, canSell, canLoan, sellable: [...] }`.
- 대출 원금(은행 유출)과 압류된 월급(은행 유입)도 돈의 보존 불변식에 포함된다.

## 7. 페이즈 상태기계 (Game)

`AWAIT_ROLL` → (이동/칸 해석) → `AWAIT_BUY` | `AWAIT_BUILD` | `AWAIT_START_BUILD` | `AWAIT_ACQUIRE` | `AWAIT_CASINO` | `AWAIT_LIQUIDATION` | `AWAIT_ISLAND_CHOICE` | `AWAIT_TRAVEL` → `TURN_END`(더블이면 같은 플레이어 `AWAIT_ROLL`) → 다음 플레이어 … `GAME_OVER`.

- 모든 커맨드는 도메인 이벤트 목록(예: `DICE_ROLLED`, `MOVED`, `SALARY_PAID`, `TOLL_PAID`, `TICKET_DRAWN`, `CASINO_RESULT`, `BANKRUPT` …)을 남겨 UI가 로그/연출에 사용.

## 8. UI 요구사항

- 정사각 보드(11×11 그리드 외곽 40칸), 중앙에 주사위·행동 버튼·최근 이벤트·잭팟 적립금 표시.
- 칸에 소유자 색 띠, 건물 단계 아이콘, 말(토큰) 표시. 말 이동은 한 칸씩 애니메이션.
- 우측(모바일은 하단)에 플레이어 패널(현금/자산/상태), 게임 로그.
- 모달: 구매/건설/통행료 안내/행운 티켓 뒤집기/카지노(3종 탭, 베팅 슬라이더, 슬롯 릴 연출)/공항 목적지 선택(보드 칸 클릭)/정리 매각/게임 종료 순위.
- 시작 화면: **방 만들기 / 방 목록에서 참가 / 코드로 참가**, 이전 방 재접속.
- 로비: 방 코드와 LAN 접속 주소 크게 표시, 좌석 목록(온라인 표시), "이 기기에서 플레이어 추가"(핫시트), 호스트 전용: 컴퓨터 추가/라운드 제한/시작.
- 게임 중: 내 기기의 좌석 차례일 때만 행동 버튼 활성화, 남의 차례에는 관전(같은 연출이 모든 기기에서 재생). 모바일 세로 화면 대응 필수.
- 이미지 에셋 없이 CSS + 이모지/인라인 SVG만 사용. 키보드 접근성(버튼 포커스, Space/Enter로 주사위).

## 10. 결정 사항 (구현 중 확정한 규칙)

명세가 모호했던 부분은 **가장 단순하고 일관된 규칙**을 골라 구현하고 여기에 기록한다.

### v2 규칙 변경 (프로젝트 오너 지시로 개정)

1. **건물 모델 교체**: Lv1→Lv3 선형 업그레이드를 폐기하고, 독립 건물 3종(별장/빌딩/호텔) + 관광명소 모델로 변경. 건설비 0.3/0.6/0.9/1.0, 통행료 배율 0.1 + 0.3/0.6/1.0(3종 = 2.0), 관광명소 3.5 고정. (명세 4장 "도시(CITY)")
2. **건설 기회(build opportunity)** 개념 도입: 한 번의 기회에 원하는 조합을 한꺼번에 건설. 3종을 완성한 그 기회에서는 관광명소를 짓지 못한다. 기회는 매입 직후 / 내 도시 도착 / 인수 직후 / 출발 칸 보너스에 주어진다.
3. **출발 칸 보너스** 신설: 출발 칸에 정확히 도착하면 내 도시 한 곳에 건설 기회 1회.
4. **인수(ACQUISITION)** 신설: 관광명소 없는 남의 도시는 통행료를 전액 낸 뒤 투자액 × 2로 인수 가능(현금만, 소유자는 거절 불가).
5. **지불 불능 규칙 교체**: 현금 부족은 즉시 파산이 아니다. `AWAIT_LIQUIDATION`에서 `SELL`/`AUTO_SELL`/`TAKE_LOAN`(게임당 1회, 원금 1,000,000 / 채무 1,200,000, 월급 압류로 상환)/`DECLARE_BANKRUPTCY`를 반복 선택한다. 파산은 플레이어의 명시적 선언으로만 발생한다.
6. **AutoPlayerPolicy 갱신**: 건설 후 현금 300,000원 이상 유지, 관광명소는 현금 ≥ 2배, 인수는 현금 ≥ 3배, 지불 불능은 자동매각 → 대출 → 파산 순.
7. **바퀴(lap)별 건설 제한 도입**(실제 플레이 피드백 반영): 처음부터 호텔까지 짓지 못한다. **1바퀴 별장 / 2바퀴 빌딩 / 3바퀴부터 호텔**이며 종류는 누적된다. 바퀴는 월급을 받는 상황마다 오른다(명세 3장). 규칙은 도메인(`Player.lap`, `City.buildableTypes({lap})`, `BuildingUnlocks`)에만 존재하고, 서버가 모든 BUILD/START_BUILD 페이로드를 검증한다. (명세 4장 "바퀴별 건설 제한")

| D23 | 관광명소와 바퀴 | 관광명소는 **바퀴로 막지 않는다**(기존 규칙 유지: "그 기회가 시작될 때 3종이 모두 있는가"만 본다). 스스로 3종을 다 지으려면 3바퀴가 필요하지만, **인수로 넘겨받은 건물이 섞여 3종이 채워지면 1·2바퀴 플레이어도 관광명소를 지을 수 있다**(3종이 완성된 도시를 인수한 경우, 또는 일부가 지어진 도시를 인수해 그 바퀴에 열린 나머지를 직접 지어 3종을 채운 경우). 인수는 이미 "투자액 × 2를 현금으로" 치르는 값비싼 행동이라, 여기에 바퀴 제한을 더하지 않는 쪽이 단순하다 |
| D24 | 바퀴 수가 없는 예전 스냅샷 | `players[].lap`이 없으면 **1바퀴로 복원한다**(위치·라운드로 바퀴 수를 추정하지 않는다 — 추정은 어차피 정확할 수 없고, 1바퀴는 가장 보수적인 값이다). 값이 있으면 1 이상 정수만 받는다 |
| D25 | 잭팟 적립금 수령 티켓(실제 플레이 피드백 반영) | 잭팟은 세관·세무조사·카지노 패배로 계속 쌓이는데 나가는 길이 슬롯 7️⃣7️⃣7️⃣(1/216) 하나뿐이라 **판이 끝날 때까지 한 번도 지급되지 않는 일이 흔했다**(골든 리플레이 16판: 판 종료 시 남은 적립금 평균 452,112원, 슬롯 지급 0회). 그래서 행운 티켓에 수령권 2장을 넣었다 — `T21 잭팟 당첨권`(전액)과 `T22 잭팟 나눔 행사`(절반). 규칙: ① 지급액은 `floor(적립금 × share / 100)`이고 **내림에서 흘린 원은 적립금에 남는다**(지급액 + 남은 적립금 = 수령 전 적립금, 그래서 총합이 보존된다). ② 적립금이 0원이면 **아무 돈도 움직이지 않는다** — 위로금을 은행에서 꺼내 주면 잭팟 티켓이 "은행에서 돈 받는 티켓"이 되어 경제가 흐려지므로, 금액 0원 이벤트만 남기고 "적립금이 비어 있었다"고 알린다. ③ 돈은 `counterparty: JACKPOT` 이동이라 **총합(현금 + 잭팟)을 바꾸지 않고 은행 장부에 남지 않는다**. 사유는 새로 만들지 않고 `TICKET`을 쓴다(장부에 기록되지 않는 이동이라 사유별 내역에 나타날 일이 없고, `MONEY_REASONS`를 넓히면 저장 스키마 승급이 따라온다 — 11.6). ④ 계산 규칙은 적립금의 주인인 `Casino.claimShare()`가, "어떤 지분을 청구하는가"는 `TicketEffects`가 소유한다(서비스 레이어에 규칙을 두지 않는다). ⑤ 알림은 새 이벤트 `JACKPOT_CLAIMED {playerId, amount, share, remaining}`이며, 적립금이 실제로 줄었으면 기존 `JACKPOT_CHANGED`가 뒤따른다. ⑥ 즉시 효과라 결정 페이즈가 없으므로 `AutoPlayerPolicy`는 바뀌지 않는다. 티켓 추가 뒤 같은 골든 16판의 남은 적립금 평균은 164,252원으로 내려갔고(3판은 정확히 0원), 라운드·커맨드 수는 거의 그대로다(30.5 → 30.25 / 248.7 → 247.6) |
| D26 | 새 티켓이 없는 예전 덱 스냅샷 | 덱 스냅샷은 **남은 티켓 id 목록**이라, 20장 시절에 저장된 방은 그대로 열리고 그 더미를 다 쓸 때까지는 새 카드가 나오지 않는다. 더미가 비어 **다시 채우는 순간 카탈로그 전체(22장)로 채워지므로** 그때부터 새 카드가 섞인다. 저장된 방을 손대 카드를 끼워 넣지 않는 쪽이 단순하고, 판 중간에 덱 구성이 바뀌는 놀라움도 없다(`tests/integration/jackpotTicketSnapshot.test.js`의 예전 덱 픽스처가 이를 증명한다) |

## 11. 금융 확장 대비 구조 (브랜치 0 — `refactor/game-money-seams`)

주식·대출·코인·파생·성적표를 **가산만으로** 얹을 수 있도록 미리 뽑아 둔 시임(seam)이다.
게임 규칙은 하나도 바뀌지 않았다 — 같은 시드의 진행·최종 순위·이벤트 순서가 리팩터 전과
바이트 단위로 같다는 것을 `tests/e2e/goldenReplay.test.js`(골든 리플레이)가 증명한다.

god object를 피하는 세 가지 규칙:

- **R1. Game은 규칙을 모른다.** Game은 위임만 한다. 가격·심사·정리 순서 규칙은 해당 엔티티/도메인 서비스 안에 있다.
- **R2. 서브시스템은 돈을 직접 만지지 않는다.** 모든 서브시스템 메서드는 `{ intents, events }`만 돌려주고, `Treasury.apply(intents)`만 실제로 옮긴다.
- **R3. 확장은 포트 등록으로.** 새 자산군은 `AssetRegistry.register(...)` 한 줄이면 총자산·정리 매각·파산 청산·순위에 동시에 반영된다.

### 11.1 Treasury와 MoneyIntent — 돈 이동의 유일한 통로

```js
MoneyIntent = { playerId, amount, counterparty, otherPlayerId, reason, meta }
//  amount  +면 수령, −면 지불 (원 단위 정수, |amount| ≤ MAX_MONEY = 1조)
//  counterparty  BANK | EXCHANGE | JACKPOT | PLAYER
//  reason        MONEY_REASONS (shared/MoneyIntent.js 단일 출처)
```

- `Treasury.apply(intents)` **한 번이 원자적인 한 건의 이동**이다. 파산 분배나 「생일 축하」처럼
  지불과 수령이 짝을 이루는 흐름은 반드시 한 번의 `apply()`로 묶는다 — 불변식은 호출 경계에서 검사한다.
- `counterparty ∈ {BANK, EXCHANGE}`만 장부에 기록한다(거래소도 은행 창구다). 좌석 간 이동과
  잭팟 이동은 총합을 바꾸지 않으므로 기록하지 않는다.
- `Player.pay/receive`, `BankLedger` 기록, `Casino.accumulate/payOut`은 **`Treasury`만 호출한다.**
  `tests/unit/moneyPaths.test.js`가 `src/` 전체를 훑어 이 규칙을 강제한다(새 파일이 생겨도 자동으로).
- `Casino.play()`는 **판정만 하는 순수 함수**다(잭팟을 바꾸지 않는다). 무엇을 어떻게 옮길지만 알려준다.

**돈의 보존 불변식이 2단이 됐다** (`moneyReport()`):

1. `총현금 + 잭팟 = 초기총액 + 은행순유입` (기존, D14)
2. `은행순유입 = Σ 사유별 내역(breakdown)` — 어긋나면 **어떤 흐름이 장부를 우회했는지** 바로 특정된다.

> 예외: `schemaVersion` 1 시절 저장된 방은 과거 순유입의 사유를 되살릴 수 없어 `breakdown`이 비어
> 있다. 그 방만 `breakdownBalanced === false`이고(`ledger.unattributedNet`으로 드러난다),
> 1번 불변식은 그대로 성립한다.

### 11.2 RoundClock — 라운드 전이와 틱 훅

`RoundClock.advance()`의 순서를 명시적으로 고정한다. 시장·대출·파생·리포트는
`Game.registerRoundTickHook(hook)`으로 **구독만** 한다.

```
1) 다음 생존 좌석 탐색 (배열 인덱스가 끝을 넘으면 = 라운드 경계. 탈락자 수와 무관하게 정확)
2) 못 찾으면 GAME_OVER(LAST_SURVIVOR)
3) 한 바퀴를 돌지 않았으면 → 턴 시작. 틱 없음
4) 한 바퀴를 돌았으면 → round += 1, ROUND_ADVANCED 발행
5) 라운드 제한 도달 → GAME_OVER(ROUND_LIMIT).  ★ 틱을 돌리지 않는다
6) 틱 훅 실행 (등록 순서)
7) 턴 시작
```

- **더블 추가 턴에는 틱이 없다** — `#endTurn`이 `advance()`를 부르지 않으므로 구조적으로 보장된다.
- **라운드 제한으로 끝나는 전이에서 틱이 없는 이유**(5번이 6번보다 먼저): 틱은 "이제 시작할 라운드"에
  속한다. 절대 플레이되지 않는 라운드의 사건으로 최종 순위가 뒤집히면 부당하다.
- 훅은 `{ intents, events }`만 돌려준다(R2). 적용은 Game이 `Treasury`로 한다.

### 11.3 AssetRegistry와 자산군 포트(AssetProvider)

```js
AssetProvider = { kind, liquidationPriority, listOf(playerId), valueOf(playerId),
                  liquidate({playerId, assetId, quantity}), releaseAllOf(playerId) }
```

- `liquidationPriority`는 **작을수록 먼저 팔린다**(설계 순서: 파생 → 코인 → 주식 → 예금 → 부동산).
  부동산(`PropertyAssets`)은 100으로 가장 뒤다.
- 자동매각 순서는 `Liquidator`에 세 줄로 고정돼 있다: 자산군 우선순위 → 환급액 낮은 것 → 목록 순서.
- **총자산은 `NetWorth` 한 곳에서만 계산한다.** `Game.rankings()`와 `application/dto.js`의
  `totalAssets`가 같은 함수를 쓴다(예전에는 같은 공식이 두 곳에 복제돼 있었다).
- `Game.registerAssetProvider(provider)` 한 줄로 매각 목록·자동매각 순서·파산 청산·총자산에
  동시에 들어온다. `tests/unit/game.assetProvider.test.js`가 가짜 예금 자산군으로 이를 증명한다
  (Game.js를 고치지 않는다).

### 11.4 결제 흐름과 채무 증서

- `PaymentFlow`: 강제지불 → (부족하면) `AWAIT_LIQUIDATION` → 정산 → 이어하기. 페이즈 전이는 하지
  않고 "무엇이 필요한지"(결과 종류 + 발행할 이벤트 + 이어갈 흐름)만 돌려준다.
- `DebtNote`(VO): 합계·대표 채권자·돈 이동 의사·저장 형태를 스스로 안다. 받을 사람이 탈락했으면
  은행이 받는다(탈락 좌석에 주면 `eliminate()`에서 그 돈이 사라진다).
- `Bankruptcy`: 남은 현금 분배(D20)와 전 자산군 청산.
- `LapIncome`: 출발 통과 1회 정산 = **한 바퀴 완주**. 앞으로 이동하며 출발 칸을 지나거나 도착했을 때만
  호출되므로(`Board.advance()`의 `passedStart`), **바퀴 증가(D22)도 여기가 소유한다** — 한 바퀴를
  마쳤다는 사실과 그 대가인 소득은 같은 사건이고, 월급이 전액 압류돼도 바퀴는 올라야 하기 때문이다.
  `LAP_ADVANCED`를 월급 이벤트보다 먼저 낸다. 지금은 바퀴 증가 + 월급 + 대출 압류뿐이며,
  **배당·분할상환이 붙을 지점**이다.

### 11.5 행동 주체(acting seat)와 커맨드 표

- `COMMAND_PHASES`(어떤 페이즈인가) + `COMMAND_OWNERSHIP`(누가 보낼 수 있는가) 이중 검증.
  지금은 모든 커맨드가 `CURRENT_PLAYER`다.
- `Game.actingSeatId`는 **지금 결정을 내릴 좌석**이며 오늘은 항상 턴 소유자와 같다. 앞으로 압류 경매처럼
  턴 소유자가 아닌 좌석이 결정하는 구간이 생기면 이 값만 달라지고 `currentSeatId`는 턴 소유자로 남는다
  — 자동 진행 드라이버·SSE·뮤텍스 모델을 흔들지 않는다. DTO에 `view.actingSeatId`로 실린다.

### 11.6 방 옵션과 저장 스키마

- `options.finance = { investmentMode, financeSystem, tradeTimerSec, scenario }`, 기본값은 전부 꺼짐
  (`OFF` / `BASIC` / `0` / `STANDARD`). **아직 구현되지 않은 값은 거부한다**(`ERR001`) — 켤 수는 있는데
  아무 일도 일어나지 않는 옵션을 만들지 않는다. 기능이 들어올 때 `ALLOWED_FINANCE_OPTIONS`에 값을 추가한다.
- 옵션은 **대기실에서만** 바꿀 수 있다. `START` 시점의 옵션이 판 내내 고정된다 — 밸런스·불변식이 판
  중간에 바뀌면 안 된다.
- `schemaVersion: 2`. 없으면 1로 보고 `migrateRoomSnapshot()`이 단계별로 올린다(v1 → v2는 금융 옵션
  기본값 채우기). `deserializeRoom` = 승급 → 검증 → 복원.
- **미래 버전 파일은 거부하되 손대지 않는다.** 손상(`RoomSchemaError` → 격리)과 달리 "이 서버보다
  새로운 파일"(`RoomVersionError`)은 멀쩡하므로 **건너뛰기만** 하고 이름을 바꾸지 않으며, 그 방 코드는
  예약된 것으로 취급해 새 방이 차지하지 못하게 한다. 거부의 목적이 "롤백 한 번에 판을 잃지 않는 것"이라
  격리해 버리면 그 목적이 무너지기 때문이다.
- **허용 값 목록을 넓히는 변경은 `ROOM_SCHEMA_VERSION` 승급과 함께 가야 한다.** 구버전 서버는 모르는
  값을 담은 파일을 손상으로 보고 격리한다(`tests/unit/financeOptions.test.js`가 이 약속을 지킨다).
- 금액 필드는 검증기도 도메인과 **같은 범위**(`Number.isSafeInteger` + `MAX_MONEY`)만 통과시킨다.
  `1e300`이나 `2^53+1`이 통과하면 복원된 방의 보존 불변식이 처음부터 거짓이 되거나 값이 조용히 달라진다.
- 건설·인수 대상 칸은 범위뿐 아니라 **소유 가능한 칸인지**까지 검증한다. `buildIndex: 0`(출발 칸) 같은
  스냅샷이 통과하면 그 방은 조회·SSE·자동 진행이 영구히 실패하면서도 격리되지 않는다.
- 검증기는 서브시스템별로 쪼개져 있다(`GAME_SUBSYSTEM_VALIDATORS`). 다음 Phase는 이 목록에 한 줄만
  추가한다.

## 12. 증권거래소 (투자 모드 `STOCKS`) — 브랜치 1 `feature/stock-market`

방 옵션 `options.finance.investmentMode`를 `"STOCKS"`로 켠 방에서만 동작한다. `"OFF"`인 방은
**행동이 한 바이트도 달라지지 않는다** — 골든 리플레이 16시나리오(`tests/e2e/goldenReplay.test.js`)가
무수정으로 통과하는 것이 그 증거다. 증권거래소 자신의 회귀는 별도 골든
(`tests/e2e/goldenReplayStocks.test.js`)이 지킨다.

설계 원칙 세 줄(11장의 R1·R2·R3를 그대로 따른다):

- **Game은 가격·한도·수수료 규칙을 모른다.** `market.buy(...)`처럼 위임만 한다.
- **시장은 돈을 직접 만지지 않는다.** 모든 메서드가 `{ intents, events }`만 돌려주고
  `Treasury.apply()`만 실제로 옮긴다.
- **주식·예금은 `AssetProvider` 등록 한 줄**로 총자산·정리 매각·자동매각 순서·파산 청산에 들어온다.

| `NRG` | 청해에너지 | 에너지 | 20,000 | 500bp | 350 |

예비 상장 풀(상장폐지 대체용, 이 순서로 상장): `SKY` 새벽항공운수(9,000 / 800bp / 100) ·
`ROCK` 반석중공업(11,000 / 850bp / 150) · `LEAF` 초록전력(14,000 / 550bp / 300).
**예비 종목의 숫자는 설계서가 이름만 정했으므로 이 구현에서 확정했다**(대체하는 섹터의 원래 종목과
비슷한 성격이 되도록).

주식 클래스 파라미터: 가격 단위 100원 / 하한 기준가의 20% / 상한 400% / 상장폐지 임계 20%.
코인(500원 / 5% / 1000% / 10%)과 지수 파라미터도 **미리 표에 넣어 두었다** — Phase 3·4가
데이터만 추가해 열 수 있다.

**틱 공식(정수 연산만, 난수는 `shockBp` 한 번뿐)**

```
volBp   = floor(baseVolBp × volMulPct / 100)
shockBp = random.nextInt(-volBp, +volBp)
nudgeBp = clamp(누적 보드 압력, ±600)
tickBp  = clamp(driftBp + newsBp + nudgeBp + shockBp, ±4000)      // 한 라운드 최대 ±40%
next    = round_half_up(price × (10_000 + tickBp) / 10_000, tickUnit)
price'  = clamp(next, floor(기준가 × 20%), floor(기준가 × 400%))   // 경계도 tickUnit 배수
```

- 가격은 **항상 정수이고 `tickUnit`의 배수이며 경계 안**이다(무작위 10,000틱 속성 테스트).
- 하한이 곧 상장폐지 임계이므로, 하한에 닿은 종목은 그 자리에서 상장폐지된다.
- **주문은 이 식에 등장하지 않는다.** 거래소가 무한 유동성 상대방이라 시세 조작이 불가능하다.

### 12.2 경기 국면과 뉴스

| 국면 | 추세(bp/라운드) | 변동성 배수 | 전이 확률 | 평균 길이 |
|---|---|---|---|---|
| 호황 EXPANSION | **+200** | 100% | 35% | 3.9라운드 |
| 과열 OVERHEAT | **+100** | 140% | 50% | 3.0라운드 |
| 침체 RECESSION | **−150** | 130% | 35% | 3.9라운드 |
| 회복 RECOVERY | **+150** | 80% | 40% | 3.5라운드 |

- 순환은 호황 → 과열 → 침체 → 회복이며 **최소 2라운드**는 머문다. 한 순환 ≈ 14라운드라
  25라운드 판에서 5~6국면을 지난다. 판은 **회복 국면**에서 시작한다(규칙을 배우는 동안 큰 손실을
  보지 않게).
- 뉴스는 **국면별 덱 6장씩, 전체 24장**이며 비복원 추출 + 소진 시 리셔플이다. 그래서 뉴스는
  독립 난수가 아니라 **국면의 함수**이고, 침체에 호황 뉴스가 나오지 않는다.
- **기준금리는 뉴스의 `RATE` 효과만이 움직인다**(단일 출처). 시작 **50bp**, 범위 25~400bp.
- 뉴스 24장의 문구와 bp는 설계서 §3.3 그대로이며, 카드마다 **파라미터화 단위 테스트**가 있다.

### 12.3 오너 밸런스 결정과 튜닝한 상수

> 오너 지시: "등락은 있어도 장기투자 하면 자산이 꾸준히 오르는 시스템",
> "**1바퀴 평균 6~7% 상승**(물론 떨어질 때도 있어야 함)".

설계서 원안(§3.2)의 기대수익은 라운드당 약 **+0.37%**(1바퀴 ≈ +2%)로 목표에 못 미쳤다.
**바꾼 상수는 두 개뿐**이다:

| 상수 | 설계서 원안 | 확정값 | 이유 |
|---|---|---|---|
| 국면별 추세 `driftBp` | 150 / 50 / −200 / 100 | **전 국면 +50bp 균일 가산** (200 / 100 / −150 / 150) | 기대수익만 평행이동시킨다. 국면 간 상대 관계·침체의 명확한 하락·뉴스 카드 문구를 하나도 건드리지 않는다 |
| 기준금리 시작값 | 100bp | **50bp** | 주식 기대수익을 올렸으므로 **무위험 자산이 이를 따라붙지 않게** 낮췄다. 범위(25~400bp)와 "뉴스만이 금리를 움직인다"는 규칙은 그대로. Phase 2의 대출금리 하한(기준금리 +200bp) 관계도 그대로 유지된다 |
| (부수) 자동 좌석 예치 기준 | 250bp | **125bp** | 250bp는 "시작 금리 100bp의 2.5배"였다. 시작값이 절반이 됐으므로 같은 배수를 유지했다. 그대로 두면 자동 좌석이 한 판 내내 예금을 쓰지 않아 예금 경로가 죽는다 |

**국면마다 다른 값을 주지 않고 같은 값을 더한 이유**: 국면의 성격(어느 국면이 좋고 나쁜지, 침체가
얼마나 매서운지)은 설계서가 정한 **게임 규칙**이다. 균일 가산은 기대수익만 옮기므로 규칙을 보존한다.
뉴스 카드의 효과 크기는 **건드리지 않았다**.

**시뮬레이션 결과** — 시드 300개 × 25라운드, 5종목 동일 비중 매수 후 보유, 보드 압력 제외.
실제 `Market.roundTick()`을 돌린 값이며 시드가 고정이라 **결정적**이다
(`tests/e2e/marketBalance.test.js`가 이 수치를 지키고, `node scripts/dumpMarket.js --summary`로 재현한다).

| 항목 | 값 | 목표 |
|---|---|---|
| **1바퀴(5.5라운드) 평균 수익률** | **+6.17%** | +6~7% ✔ |
| 1바퀴 **중앙값** 기준 수익률 | +5.79% | 참고(평균은 큰 상승에 끌려 올라간다) |
| 라운드당 평균 수익률 | +1.09% | +0.9~1.4% ✔ |
| 25라운드 평균 / 중앙값 | +31.28% / +29.20% | +25~45% ✔ |

| 배당 포함 평균 수익률 | +42.96% | 예금보다 분명히 높을 것 ✔ |

| 종목 | 평균 | 중앙값 | 손실 확률 | 상장폐지율 | 평균 종가/기준가 |

| CON | +38.42% | +31.25% | 22.67% | 0% | 1.38배 |
| HOT | +35.93% | +30.67% | 16.33% | 0% | 1.36배 |

읽는 법(교육 목표와 직결):
- **분산 포트폴리오의 손실 확률(7.7%)이 모든 개별 종목(15.7~27%)보다 낮다** — 분산투자의 교훈이
  숫자로 드러난다. 테스트가 이 부등호를 종목마다 강제한다.
- **변동성이 큰 종목일수록 손실 확률이 높다**(ENT 1200bp → 22% vs NRG 500bp → 15.7%). ENT는 무배당의 대가로 평균 가격 수익률(+52.5%)이 5종목 중 가장 높고, **경기 방어 종목**이다(D43·D44).
- **25라운드 안의 상장폐지는 0%**다. "꾸준히 오른다"는 목표와 "가끔 휴지조각이 된다"는 목표는
  25라운드 지평에서 양립하지 않으므로, 오너의 최신 지시(전자)를 따랐다. 상장폐지·재상장 규칙이
  죽은 코드가 아님은 ① 강제 단위 테스트 ② **100라운드 시뮬레이션에서 실제로 발생**함으로 증명한다.

### 12.4 거래 창구 `AWAIT_TRADE`

자기 턴이 시작된 직후, **조난 선택·공항 목적지·주사위보다 먼저** 한 번 열린다.

```
TURN_STARTED → TRADING_OPENED → (예약 주문 자동 체결) → 주문/예금 반복
             → CLOSE_TRADING 또는 예산 소진 자동 마감 → TRADING_CLOSED
             → 원래 흐름(ISLAND | TRAVEL | ROLL)
```

- **조난 중에도 열린다**(죽은 턴을 만들지 않는다). 닫으면 조난 선택으로 간다.
- **거래할 것이 전혀 없으면 열리지 않는다**: 현금 0 + 보유 0 + 예금 0.
- **더블 추가 턴에는 창구가 없다.** `#endTurn`이 `#beginTurn`을 부르지 않으므로 구조적으로 보장된다.
- 창구를 닫은 뒤 돌아갈 곳은 `turn.afterTrade`에 담기고 **스냅샷에도 저장된다**.
- **열린 창구와 남은 예산도 저장한다** — 저장하지 않으면 새로고침으로 예산을 되돌려 무한히
  거래할 수 있다(실제로 막은 악용 경로).

| 한도 | 값 |
|---|---|
| 창구당 주문 수 | **없음**(D46; 원래 3건) |
| 창구당 총 명목금액 | **없음**(D46; 원래 2,000,000원) |
| 주문 1건 명목금액 / 수량 | ≤ 1,000,000원 / 1~200주 |
| 종목별 보유 상한 | 500주(매점 차단) |
| 거래 수수료 | `max(1,000, ceil(명목금액 / 100))` — 1%, 최소 1,000원, **매수·매도 양방향** |
| 예금 단위 / 상한 | 10,000원 / 10,000,000원 |
| 예약 주문 | 좌석당 3건, 체결 시점에 전면 재검증 |

**예치·인출은 주문 건수만 쓰고 명목금액 예산은 쓰지 않는다.** 예금 상한이 10,000,000원인데
명목 예산(2,000,000원)에 넣으면 규칙끼리 모순되기 때문이다(구현에서 확정한 결정).

### 12.5 돈의 흐름과 익스플로잇 차단

새 사유 6종: `TRADE_BUY` `TRADE_SELL` `TRADE_FEE` `DIVIDEND` `DEPOSIT` `DEPOSIT_INTEREST`.
모두 `EXCHANGE`/`BANK` 상대이므로 **기존 보존 불변식의 형태가 그대로다**
(`총현금 + 잭팟 = 초기총액 + 은행순유입`). 예금·주식은 현금이 아니라 은행이 보관하는 채무다.

| 익스플로잇 | 차단 방법 |
|---|---|
| 대출→예금 캐리 트레이드 | 이자 대상 = `max(0, 예금 − 총부채)`. **대출이 있으면 이자가 0**이다 |
| 수수료 면제 정리 매각으로 대량 현금화 | 정리 매각은 **부족액을 덮는 수량까지만**(`quantityCovering` 포트). 작은 채무를 만들어 전량을 털 수 없다 |
| 매도 수수료를 못 내는 주문으로 돈 만들기 | `sell`이 `현금 + 명목 ≥ 수수료`를 검증하고, `Treasury.apply`가 **전량 사전 검증 → 일괄 적용**으로 원자적이다(중간 실패가 앞의 이동을 남기지 않는다) |
| 예약 주문 반복으로 자동 진행 방해 | 낙관적 동시성 토큰을 `stateVersion`으로 분리했다 — 게임 상태를 바꾸지 않는 커맨드는 대행 결정을 무효화하지 못한다 |
| 예약 주문 id 소진으로 기능 마비 | 주문 id 자리수를 현실적으로 도달 불가능하게 두고, 거절된 요청은 번호를 앞으로 밀지 않는다 |
| 반올림으로 돈 만들기 | 전액 정수. 유리한 산출(배당·이자·환급)은 내림, 불리한 산출(수수료)은 올림 |
| 같은 창구 왕복거래 | 가격이 고정이고 수수료가 양방향이라 **항상 손실**(수량 1~200주 전수 속성 테스트) |
| 내부정보(보드 연동) | 압력은 **다음 틱**에 반영되고 `pendingNudges`로 전원 공개 |
| 시세 조작 | 주문이 가격에 영향을 주지 않는다 |
| 매점으로 상대 차단 | 종목별 500주 상한 |
| 거래로 판 늘리기 | 창구 3건 + 명목예산 + 소진 시 자동 마감 + 더블 추가 턴에는 창구 없음 |
| 정수 오버플로·음수·NaN | 컨트롤러 화이트리스트 + 도메인 2차 검증 + `Number.isSafeInteger` + `MAX_MONEY` |
| 남의 턴·남의 좌석 행동 | `COMMAND_PHASES` + `COMMAND_OWNERSHIP` 이중 검증 |
| 예약 주문으로 창구 우회 | 체결 시점에 현금·한도·상장·예산 **전면 재검증**, 실패하면 그 주문만 버린다 |
| 새로고침으로 예산 되돌리기 | 열린 창구와 남은 예산을 스냅샷에 저장 |
| 주문 스팸(DoS) | 좌석당 5초 10건 토큰 버킷(`ERR019`). 판을 멈출 수 있는 커맨드는 제한 대상에서 제외 |

### 12.6 보드 연동 압력(nudge)

보드 사건이 섹터에 압력을 남기고 **다음 라운드 틱에** 반영된다. 즉시 반영하면 "내 턴에 건설주를
사놓고 랜드마크를 지어 즉시 상승"이 성립해 내부정보 거래가 되므로 미룬다. 적립분은 전원에게 공개된다.

| 보드 사건 | 압력 |
|---|---|
| `LANDMARK_BUILT` | 건설 +300 |
| `CITY_PURCHASED`(가격 ≥ 300,000) | 건설 +100 |
| 잭팟 당첨 | 카지노·엔터 +800 |
| 잭팟 누적 1,000,000 돌파 | 카지노·엔터 +200 |
| 휴양지 통행료 발생 | 호텔 +100 |
| 공항 이동권 사용 | 항공 +200 |
| 세관 납부 | 전 종목 −100 |

섹터별 합계는 ±600bp로 묶이고, 틱에 반영되면 비워진다. 표는 `market/BoardNudges.js`가 소유하며
Game은 "이런 일이 있었다"는 이벤트만 넘긴다.

### 12.7 배당·정리·파산

- **배당은 출발 칸 통과 시**(월급과 같은 순간, 월급 **다음**) 상장 종목에만 지급된다.
  1주 배당 = `floor(현재가 × 배당률 / 10,000)`. 소유 지점은 `LapIncome`이다 —
  Phase 2의 대출 분할상환이 붙을 곳도 여기다.
- **정리 매각 순서는 주식(30) → 예금(50) → 부동산(100)**이다. 자산군 안에서는 환급액이 낮은
  것부터, 그마저 같으면 목록 순서. 번호 사이를 비워 두었으므로 파생(10)·코인(20)이 나중에
  끼어들어도 기존 값을 고치지 않는다.
- 새 커맨드 `SELL_ASSET { assetKind, assetId, quantity? }`로 자산군을 가리지 않고 판다.
  기존 `SELL { cityIndex }`는 하위호환으로 유지된다.
- **정리·파산 매각은 수수료가 면제되고 창구 한도를 보지 않는다**(강제 지불을 메우는 매각이므로).
- **파산은 청산이 분배보다 먼저다**: 예약 주문 취소 → 주식 전량 시장가 매도 → 예금 전액 인출 →
  그 현금까지 합쳐 채권자에게 분배 → 부동산 초기화 → 탈락.
- **상장폐지는 현금을 움직이지 않는다.** 보유 수량이 전액 소각되고(`HOLDINGS_WIPED`) 그 종목을
  겨눈 예약 주문도 버려진다. **다음 틱**에 예비 풀에서 신규 상장되어 목록은 항상 5종목이다.

### 12.8 총자산(NetWorth)

```
netWorth = 현금 + 부동산 투자액 + 주식 시가 + 예금 − 남은 대출 채무
```

자산군별 평가액을 `AssetRegistry`에서 그대로 받아 더하므로 **내역과 합계가 어긋날 수 없다.**
DTO의 `players[].netWorth`가 이 내역이고 `totalAssets === netWorth.total`이다. 순위·화면·
라운드별 성적표 스냅샷이 모두 같은 계산(`NetWorth`)을 쓴다. 탈락자는 전부 0이다.

### 12.9 영속화

- `schemaVersion: 3`. v2 → v3 승급은 **투자 모드를 끈 채로**(`market: null`) 성적표 자리만
  비워 만든다 — 진행 중인 판에 기능이 갑자기 끼어들면 밸런스·불변식이 판 중간에 바뀐다.
- `game.market`과 `game.report`가 스냅샷에 추가되고, `GAME_SUBSYSTEM_VALIDATORS`에 검증기
  두 줄이 늘었다. 검증은 **범위·타입·참조 정합성**만 본다:
  - 보유 종목이 상장 목록에 있는지, 보유·예금·예약 좌석이 방에 있는지(참조 정합성)
  - `AWAIT_TRADE` ⟺ 열린 창구가 있는지(페이즈-상태 정합성)
  - 뉴스 덱에 그 국면의 카드만 있는지, 금액이 단위·범위 안인지
  값의 "합리성"은 보지 않는다 — 과도한 엄격함은 **멀쩡한 방을 격리해 진행 중인 판을 잃게** 한다
  (거짓 양성 방어 테스트가 실제 대전의 모든 중간 상태를 통과시킨다).
- **성적표(`MatchRecorder`)는 Phase 1부터 가동한다.** 라운드별 자산 스냅샷 + 하이라이트(상한 200)
  + 사유별 손익을 모으며, **스냅샷에만 저장되고 `view`에는 실리지 않는다**(SSE 페이로드를 키우지
  않는다). 사유별 손익은 `Treasury`의 관찰자로 모으므로 — 돈이 움직이는 길이 하나뿐이라 —
  어떤 흐름도 집계를 빠져나갈 수 없다. 이걸 지금 넣지 않으면 Phase 5가 재작업이 된다.

### 12.11 코드리뷰에서 고친 것(기록)

두 번의 독립 코드리뷰(종합 리뷰 + 보안 리뷰)에서 나온 지적을 반영했다. 설계 원칙(R1/R2/R3,
틱 시점, 예산·권한 이중 검증, OFF 모드 무변경)은 두 리뷰 모두 실측으로 건전하다고 확인했다.

| 심각도 | 결함 | 왜 위험했나 |
|---|---|---|
| HIGH | `TradingDesk.sell`이 수수료 지불 능력을 검증하지 않음 + `Treasury.apply`가 intent를 한 건씩 즉시 적용 | 명목금액이 최소 수수료보다 작으면 `+명목`만 반영된 채 `−수수료`가 터져 **현금이 생기고 보존 불변식이 영구히 깨졌다.** 그 상태는 다음 커맨드에서 파일로 저장되고, 이후 모든 월급·통행료가 실패해 그 방이 죽는다(격리도 안 됨). 코인(하한가 500원)에서는 확정적으로 발생할 결함 |
| HIGH | 예약 주문이 자동 진행의 동시성 토큰을 올림 | 자기 좌석 토큰만으로 남의 턴에 예약을 반복해 **방 전체의 진행을 멈출 수 있었다** |
| MEDIUM | 정리 매각이 부족액에 묶이지 않음 | 수수료 면제 + 창구 한도 면제를 이용한 대량 현금화 |
| MEDIUM | 사유별 손익이 좌석 간 이동의 수령 측을 기록하지 않음 | Phase 5의 "손익 합 = 순자산" 검증이 원리적으로 불가능해진다 |
| MEDIUM | 검증기가 가격의 tickUnit 배수·경계를 보지 않음 | 위 HIGH의 진입 경로 |
| MEDIUM | 라운드 스냅샷 무한 증가 | 커맨드마다 방 파일 전량 재작성(쓰기 증폭) |
| MEDIUM | `sellable`의 이름 필드 키가 자산군마다 다름 | 한 배열을 렌더러 하나로 그릴 수 없다 |
| 자체 점검 | `__proto__` 좌석 키가 저장 중 조용히 사라짐 | 저장할 때 보유·예금이 없어지고 왕복이 깨진다 |
| 자체 점검 | 예약 체결의 `catch`가 프로그래밍 오류까지 삼킴 | 결함이 묻히고 플레이어의 주문만 사라진다 |
